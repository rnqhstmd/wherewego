# 알림 인프라 사용자 규모별 진화 로드맵

> Phase 8 인앱 알림함의 사용자 규모별 권장 구성과 진화 트리거. 1인 개발자 운영 환경 기준.

## 핵심 원칙

- **운영 단순성 > 이론적 최적**: 1인 개발자 환경에서 가장 큰 자산은 단순성
- **YAGNI**: 이론적 미래 확장보다 현재 명확한 필요에 대응
- **진화 트리거 기반 단계 이동**: 지표 도달 시 다음 단계로

---

## 📍 wherewego 현재 위치

- MVP 2인 커플 그룹, 출시 전 또는 초기 (예상 사용자 0~50명)
- 단일 EC2 t3.micro (Free Tier) + Vercel + Supabase PostgreSQL
- 카카오톡 챗봇 + 웹 직접 등록 양쪽 채널
- **현재 구현이 가장 적합한 위치**

---

## 사용자 규모별 5단계

### 🟢 단계 1: 0~50명 (얼리 액세스 — 현재)

**현 구현 그대로 OK.** 추가 작업 불필요.

| 지표 | 값 |
|------|-----|
| SSE 동시 연결 | 최대 ~50개 |
| Emitter 메모리 | 무시 가능 (~수십 KB × 50 = ~2.5MB) |
| DB row | 250건/일 = 9만 건/년 |
| 비용 | $0 (Free Tier 유지) |

**유일한 작업**: 의문점 3개 staging 1회 검증 (request.signal, preflightAuth, V007 FK)

---

### 🟢 단계 2: 50~500명 (정식 출시 초기)

**현 구현 + 소소한 최적화.** 큰 변경 없음.

| 작업 | 이유 | 예상 시간 |
|------|------|----------|
| EC2 → t3.small 업그레이드 | t3.micro 1GB 메모리 부족 가능 (SSE 100~150 연결) | 5분 |
| `PinRepository.findAllById` 추가 | 알림 50건×N핀 N+1 누적 | 15분 |
| `shownToastIds` LRU cap (50건) | 장기 세션 메모리 누적 방지 | 10분 |
| Micrometer SSE 연결 수 메트릭 | 운영 가시화 | 1시간 |
| `request.signal` 동작 실측 후 보강 | emitter 좀비 발견 시 30s 스케줄러로 cleanup | 측정 따라 |

비용: $8~15/월 (EC2 t3.small)

---

### 🟡 단계 3: 500~5,000명 (안정 성장 — 첫 번째 진화 트리거)

**SSE는 유지하되 인프라 보강 필요.** 카카오톡 푸시 검토 시작.

| 작업 | 이유 |
|------|------|
| EC2 → t3.medium 또는 t3.large | SSE 500~1,000 연결, 메모리 본격 부담 |
| heartbeat 주기 30s → 60s | 부하 감소 (사용자가 자주 끊김 안 느낌) |
| 알림 90일 보관 + 아카이브 스케줄러 | DB 1,800만 건/년 부담 |
| 알림 테이블 인덱스 재검토 (파티셔닝 검토) | 조회 효율 유지 |
| **카카오톡 푸시 알림 도입** | SSE 미연결 사용자(앱 비활성) 비율 증가 → 알림 무용 방지 |
| 알림 통계 (수신율/클릭율) | 제품 의사결정 기반 |

**진화 트리거**:
- 앱 비활성 사용자 알림 도달율 < 30%
- 또는 SseEmitter 메모리 > 500MB

비용: EC2 t3.medium $30~40/월

---

### 🟠 단계 4: 5,000~50,000명 (본격 스케일 — 두 번째 진화 트리거)

**SseEmitter는 단일 EC2 한계 도달. 아키텍처 변경 필수.**

| 작업 | 변경 |
|------|------|
| **SSE → WebSocket 전환** | Spring WebFlux + Reactor 또는 STOMP. 양방향 + 더 효율 |
| **Redis Pub/Sub 도입** | 알림 fan-out. EC2 다중 인스턴스 간 알림 동기화 |
| EC2 2~4대 + ELB (Load Balancer) | 수평 확장. ADR-0001 폐기 |
| 알림 테이블 월 단위 파티셔닝 | 수억 건 누적 |
| **Web Push API + Mobile Push** | 브라우저 닫혀 있어도 알림 |
| `@TransactionalEventListener` + `@Async` | 동기 호출 스레드 점유 해소 |

**진화 트리거**:
- 단일 EC2 SseEmitter 메모리 > 1.5GB
- 또는 다중 인스턴스 운영 필요성 (배포 무중단 등)

비용: AWS ELB + EC2 t3.large × 3 + ElastiCache (Redis) = $150~400/월

---

### 🔴 단계 5: 50,000명+ (대규모 — 세 번째 진화 트리거)

**알림이 별도 마이크로서비스.**

- Firebase Cloud Messaging 또는 OneSignal 같은 외부 푸시 서비스
- 알림 도메인을 별도 서비스로 분리 (gRPC/Kafka)
- 알림 데이터를 별도 NoSQL (DynamoDB / Cassandra)
- 알림 개인화/추천 (ML 기반)

이 단계는 wherewego 비즈니스 모델상 도달하기 매우 어려움 (2인 커플 + 자연어 입소문 마케팅).

---

## 단계 이동 트리거 표

| 다음 단계로 가야 하는 신호 | 측정 방법 | 다음 단계 |
|---------------------------|----------|----------|
| EC2 메모리 > 70% 지속 | CloudWatch | 단계 2 또는 3 |
| 알림 도달율 < 50% (앱 비활성) | 알림 통계 + 클라이언트 도달 로그 | 단계 3 (카카오톡 푸시) |
| MAU 5,000명 돌파 | Mixpanel/Amplitude | 단계 4 (수평 확장 검토) |
| SseEmitter 메모리 > 1.5GB | JVM 모니터링 | 단계 4 (Redis Pub/Sub) |
| 배포 시 다운타임 발생 → 무중단 필요 | 운영 사고 | 단계 4 (ELB + 다중 인스턴스) |

## wherewego 가장 편하고 좋은 결론

### 출시 전 ~ 1년 (대부분의 기간)

**현재 구현 그대로 유지 + 단계 2 작업 5개만 적용.**

이유:
- 카카오 OAuth2 + 2인 커플 그룹 = 친구 추천 기반 자연 성장 (폭발 성장 거의 없음)
- 단일 개발자 운영 → 운영 단순성이 최우선
- SSE는 카카오톡 푸시 없는 환경에서 "실시간 체감"을 가장 적은 인프라로 제공하는 최적 선택
- WebSocket/Redis Pub/Sub는 운영 복잡도 폭증 → 사용자 5,000명 이전엔 ROI 음수

### 지금 당장 추가하면 좋은 것 (단계 2 미리 적용)

| 우선순위 | 작업 | 시간 |
|----------|------|------|
| **P0 (지금)** | staging 1회 검증 (의문점 3개) | 30분 |
| **P1 (이번 주)** | `PinRepository.findAllById` 추가 | 15분 |
| **P1 (이번 주)** | `shownToastIds` LRU cap (50건) | 10분 |
| **P2 (출시 직전)** | Micrometer SSE 메트릭 + Grafana 대시보드 | 1시간 |
| **P3 (출시 후 1개월)** | `request.signal` 동작 실측 + 보강 | 측정 따라 |

### 핵심 결론

**지금은 아무것도 추가하지 말고 그대로 출시해도 됩니다.** 단계 2는 사용자 100명 넘는 시점에 들어가도 늦지 않습니다. 운영 단순성이 1인 개발자 환경에서 가장 큰 자산입니다.

진화는 **지표 기반**으로 진행하고, 예측에 따라 미리 만들지 않습니다.
