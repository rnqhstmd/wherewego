# PRD: Phase 12 — Pin Experience v2

## 1. 배경 및 문제 정의

### 현재 제품 상태

wherewego는 커플(2인) 그룹이 함께 가고 싶은 장소를 저장·관리하는 서비스다. 카카오톡 챗봇으로 인스타그램 릴스 URL을 보내면 AI가 장소를 추출해 핀으로 저장하고, 지도에서 함께 탐색할 수 있다.

현재 핀은 REEL(발견) / WISH(위시) / MEMORY(추억) 3단계 태그로 관리되며, Phase 9까지의 기능이 운영 중이다.

### 해결해야 할 문제

**문제 1 — 태그 의미 혼선**: REEL(발견)과 WISH(위시) 모두 "가고 싶다"는 뉘앙스를 가져 사용자가 어느 태그를 써야 할지 불분명하다. 두 태그 사이의 전환 조건도 명확하지 않아 "우리가 진짜 가고 싶은 곳"을 구별할 수 없다.

**문제 2 — 관심도 신호 부재**: 커플 2명 그룹에서 "좋아요"는 최대 2개뿐이라 관심도의 변별력이 없다. 한 명이 핀을 저장해도 상대방이 얼마나 관심 있는지 알 수 없다.

**문제 3 — 챗봇 다중 장소 처리 불가**: 릴스 1개에 N개 장소가 포함될 수 있으나, 현재 챗봇은 "가장 가고 싶은 곳"을 구분하는 복수 선택 플로우가 없다. 모두 동일하게 저장되거나 별도 처리 로직이 부재하다.

**문제 4 — 데이터 누적 오염**: 챗봇으로 저장된 핀 중 30일이 지나도록 아무도 관심을 보이지 않은 핀이 쌓여 지도가 노이즈로 가득 차는 문제가 발생한다.

**문제 5 — 챗봇 세션 처리 취약**: 기존 `PendingInstagramSession`은 단순 캐시 구조로, 복수 선택 / 메모 연계 / 엣지케이스(TTL 만료, 새 URL 도착, 파싱 오류)에 대한 명확한 상태 처리가 없다.

## 2. 목표 및 비목표

### 목표

1. "우리가 진짜 가고 싶은 곳"을 명확히 구분할 수 있도록 **WANT(관심 표현) 시스템**을 도입하고, 과반 달성 시 자동으로 WISH로 전환한다.
2. 지도 마커가 핀의 관심도 상태를 **즉시 시각적으로** 전달하도록 3단계 시각화를 적용한다.
3. 챗봇 릴스 저장 플로우를 **1라운드 완결** 구조로 재설계하여, 복수 장소 선택과 메모 입력을 안정적으로 처리한다.
4. 방치된 발견 핀을 **사용자 주도로 정리**할 수 있는 배너 + 일괄 삭제 기능을 제공한다.

### 성공 지표 (비즈니스 관점)

- 커플이 릴스를 저장할 때 "이 중에 어디 가고 싶어?" 대화 없이도 관심도 차이를 앱에서 확인할 수 있다.
- WISH로 전환된 핀에 대해 상대방이 별도 알림 없이도 "둘 다 가고 싶다"는 합의를 인지한다.
- 챗봇으로 10개 장소가 담긴 릴스를 보냈을 때, 사용자가 가고 싶은 곳을 선택하고 메모까지 남길 수 있다.

### 비목표 (이번 Phase에서 하지 않는 것)

- VIEW / SHARE / ROULETTE_SELECTED 액션 활성화 (Phase 12.2에서 룰렛·공유 PR과 함께)
- 관심도 가중합 정렬 공식 도입 (Phase 12.1)
- 카카오 푸시 알림 전환 (Phase 12.3, 사용자 100명+ 시점 재평가)
- WISH → MEMORY 자동 전환 로직 변경 (Phase 10 GPS 방문 감지와 동일 정책 유지)
- 핀 개별 선택 삭제 UI (기존 핀 상세 삭제 기능으로 유지)

## 3. 사용자 시나리오

### 페르소나: 2인 커플 그룹 (A, B)

#### 시나리오 1 — 챗봇으로 다중 장소 저장 후 관심 표현 → WISH 전환

1. A가 카카오톡 챗봇에 인스타그램 릴스 URL을 전송한다.
2. 챗봇이 "🗺️ 5곳 발견! 가고 싶은 번호를 콤마로 보내주세요. 1. 을지로 타코집 2. 성수 카페 ..." 안내와 함께 [전부] [건너뛰기] QuickReply를 노출한다.
3. A가 "1,3"을 입력하면 챗봇이 "메모를 남기시겠어요?" 안내 후 A가 "데이트 코스 후보"를 입력한다.
4. 1번, 3번 핀은 A의 WANT가 1로 기록된 채 저장되고, 나머지는 REEL로 저장된다. 메모는 같은 릴스의 모든 핀에 동일하게 저장된다.
5. B가 앱 지도에서 1번 핀 말풍선을 열고 [가고 싶어요] 버튼을 누른다.
6. 2인 그룹 과반(2명) 조건 충족 → 해당 핀이 REEL에서 WISH로 즉시 전환된다.
7. A에게 인앱 알림 "🌟 '을지로 타코집'이 위시로 올라갔어요! 둘 다 가고 싶어해요"가 전달된다.
8. 지도 마커가 하늘색 원형(REEL)에서 노랑 별(WISH, 1.2배)로 변경되며, 0.5초 펄스가 1회 표시된다.

**예외 흐름**: A가 WISH 전환 후 [가고 싶어요]를 다시 눌러 취소해도 핀은 WISH를 유지하고 `want_count`만 감소한다.

#### 시나리오 2 — 챗봇 단일 장소 저장

1. A가 릴스 URL을 보내고 챗봇이 장소 1개를 추출한다.
2. "📍 을지로 타코집 1곳 발견! 가보고 싶은 곳인가요?" + [가고 싶어요] [발견으로만 저장] QuickReply 노출.
3. A가 [가고 싶어요]를 누르면 메모 요청 후 저장 완료. 해당 핀은 A의 WANT가 1로 기록된다.
4. 3분 내 응답 없으면 REEL로만 저장 (D-3).

#### 시나리오 3 — 오래된 핀 정리

1. A가 `/pins` 핀 목록 화면 하단에서 "🗑️ 30일째 관심받지 못한 발견 핀이 7개 있어요" 배너를 확인한다.
2. A가 [한꺼번에 정리]를 누르면 7개 핀이 일괄 소프트 삭제된다.
3. A가 [나중에]를 누르면 7일간 배너가 노출되지 않는다. 7일 후 자동 재노출.
4. 정리 대상 조건: 챗봇 자동 저장(`memo_source=AUTO`) + 발견 태그(`tag=REEL`) + 30일 이상 경과 + 아무도 관심 없음(`want_count=0`).

**엣지**: 배너에 표시된 N개 중 일부를 B가 정리 전에 WANT를 누르면 해당 핀은 `want_count >= 1`이 되어 정리 대상에서 제외되고 배너의 숫자가 갱신된다.

#### 시나리오 4 — 관심 있는 발견 핀만 지도 필터

1. A가 지도에서 [발견] 탭을 누르면 드롭다운이 열린다.
2. "🙋 관심 있는 발견"을 선택하면 `want_count >= 1`인 발견 핀만 지도에 표시되고 탭 라벨이 "발견 (관심)"으로 변경된다.
3. 해당 핀들은 진보라(`#7B68EE`) 마커로 1.1배 크기로 표시된다.

#### 시나리오 5 — 릴스 알림에서 지도 번들 확인

1. A에게 "📍 B가 릴스에서 3곳을 저장했어요" 인앱 알림이 온다.
2. 알림 상세에서 "📍 지도에서 보기"를 누르면 `/map?reel_bundle={notificationId}`로 이동한다.
3. 방금 저장된 3개 핀이 일반 렌더링, 나머지 핀은 opacity 0.3으로 표시된다.
4. 상단 배너 "릴스 저장 핀 3개 표시 중 [해제]"에서 [해제]를 누르면 일반 지도로 복귀한다.

#### 시나리오 6 — 태그 진행 모달 (온보딩)

1. 사용자가 핀 카드/말풍선의 태그 라벨 옆 `?` 아이콘을 누른다.
2. "발견 → [가고싶어요 과반] → 위시 → [GPS 방문] → 추억" 진행 다이어그램 모달이 열린다.
3. 현재 해당 핀의 위치가 다이어그램에서 강조 표시된다.

### 4.2 비기능 요구사항

| ID | 요구사항 |
|----|----------|
| NFR-12-1 | **동시성**: WANT 토글은 `SELECT FOR UPDATE`로 pins 행을 잠근 뒤 want_count를 갱신하여 동시 클릭 시 count 불일치를 방지한다. |
| NFR-12-2 | **멱등성**: 동일 `(pin_id, user_id)` WANT는 DB UNIQUE 인덱스로 보장된다. 네트워크 재시도 시 중복 WANT가 발생하지 않는다 (D-19). |
| NFR-12-3 | **트랜잭션 격리**: WISH 전환 이벤트(`WishConvertedEvent`)는 `@TransactionalEventListener(AFTER_COMMIT)` 이후 발행되어, 트랜잭션 롤백 시 알림이 발송되지 않는다. |
| NFR-12-4 | **알림 멱등성**: 동일 핀의 WISH_CONVERTED 알림은 notifications 테이블에 1건만 INSERT된다. |
| NFR-12-5 | **챗봇 TTL 일관성**: 모든 대기 상태 TTL은 3분(`reel-selection-ttl-seconds=180`)으로 통일되며, 파싱 실패 시 TTL이 리셋되지 않아 무한 재시도를 방지한다. |

### 가정

- MVP 운영 단위는 2인 커플 그룹이며, 과반 기준(`floor(2/2)+1 = 2`)은 양쪽 모두 동의해야 WISH 전환임을 전제한다. 3인 이상 그룹 확장 시 공식(`floor(N/2)+1`)은 동일하게 적용된다
- Phase 12 기간 동안 동시 사용 그룹 수는 수십 단위로, `SELECT FOR UPDATE` 수준의 동시성 제어가 충분하다
- Gemini API 및 카카오 Local 검색 API의 외부 서비스 가용성은 Phase 12 구현 범위 외로 가정한다
- 인스타그램 릴스 URL 파싱 정확도(장소 추출 성공률)는 현재 Gemini 모델 성능에 의존하며, 본 PRD의 개선 범위가 아니다
- Phase 10(GPS 방문 감지), Phase 11(우리 기록)은 Phase 12와 독립적으로 착수 가능하다
