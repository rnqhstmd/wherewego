# PRD: Phase 13 — Pin Model 단순화 (WANT 폐기 · WISH 일원화)

> 작성일: 2026-05-28
> 선행: Phase 12 (Pin Experience v2, PR #76) — 본 Phase에서 일부 되돌림
> 상태: 작성 (사용자 4라운드 Q&A 결정 반영)

## 1. 배경 및 문제 정의

### 현재 제품 상태

wherewego는 커플(2인) 그룹이 함께 가고 싶은 장소를 저장·관리하는 서비스다. 카카오톡 챗봇으로 인스타그램 릴스 URL을 보내면 AI가 장소를 추출해 핀으로 저장하고, 지도에서 함께 탐색한다.

Phase 12에서 **WANT(가고 싶어요) 시스템**을 도입했다. 사용자가 핀에 "가고 싶어요"를 누르면 `want_count`가 증가하고, 그룹원 과반(2인 기준 2명)이 누르면 REEL → WISH로 자동 전환된다. 마커는 발견/관심/위시 3~4단계로 시각화되고, 지도 필터에 "관심" 카테고리가 추가됐다.

### 해결해야 할 문제

**문제 1 — WANT 시스템이 모호하고 이해하기 어렵다.** 2인 그룹에서 `want_count`는 0/1/2만 가능하다. 1이면 "관심", 2가 되는 순간 자동으로 WISH로 승급되어 사라진다. 따라서 "관심(INTEREST)" 카테고리는 영구히 `want_count = 1`인 좁은 슬라이스만 담으며, 사용자가 기대하는 "둘 다 관심 있는 곳"은 이 필터에 절대 들어오지 않는다.

**문제 2 — 사용자 인지 모델과 어긋난다.** 사용자가 챗봇에서 [가고 싶어요]를 눌러도 핀은 REEL(발견)로 저장되고 본인 WANT 1표만 기록된다. "가고 싶다고 했는데 왜 발견이지?"라는 인지 부조화가 발생한다. "둘 다 합의해야 위시"라는 시스템 의도와 사용자 직관 사이의 간극이 사용성 결함의 본질이다.

**문제 3 — 시각·카피가 과도하게 복잡하다.** 하트 뱃지, 펄스 애니메이션, WISH 토스트, 관심 필터, 4단계 진행 다이어그램 등 학습 부담이 큰 요소가 누적되어 있다. 커플 2인 MVP 규모에서 이 복잡도는 정당화되지 않는다.

### 해결 방향

WANT(관심 표현) 시스템을 **전면 폐기**하고, WISH의 의미를 "**누군가 가고 싶다고 표시한 곳**"(단독 의사)으로 재정의한다. 챗봇에서 [위시로 저장]을 선택하면 곧장 WISH 태그로 저장되고, 선택하지 않은 핀은 발견(REEL)으로 저장된다. 합의 기반 자동 전환·관심 카테고리·하트 시스템을 모두 제거하여 모델을 발견/위시/추억 3단계로 단순화한다.

## 2. 목표 및 비목표

### 목표

1. WANT 시스템(`pin_events`, `want_count`, `/want` API, 하트 UI, 관심 필터, 자동 전환, WISH_CONVERTED 알림)을 **완전히 제거**한다.
2. 챗봇 릴스 저장 플로우에서 **[위시로 저장] = WISH 태그 직저장**, 미선택/[발견으로 저장] = REEL 저장으로 의미를 명확히 한다.
3. 지도 마커를 **발견(파랑 원) / 위시(노랑 별) / 추억(분홍 하트) 3단계**로 단순화한다.
4. 챗봇 저장 결과·알림 본문에서 "위시 N곳 / 발견 M곳"을 **분리 표시**하여 의사 표시 결과를 즉시 인지하게 한다.

### 성공 지표 (비즈니스 관점)

- 사용자가 챗봇에서 가고 싶은 곳을 고르면, 그 핀이 즉시 "위시"로 저장됨을 챗봇 응답에서 확인할 수 있다.
- 지도·필터·말풍선에서 "관심", "하트", "둘 다 가고 싶어요" 같은 모호한 개념이 사라진다.
- 상대방은 인앱 알림에서 "위시 N곳, 발견 M곳 저장됨"을 한눈에 파악한다.

### 비목표 (이번 Phase에서 하지 않는 것)

- WISH → MEMORY 전환 정책 변경 (Phase 10 GPS 방문 감지·직접 변경 방식 유지)
- 오래된 핀 정리 기능 자체 폐기 (조건만 수정하여 유지 — D-13-7)
- 챗봇 세션 상태머신(`ReelSavedSelectionSession`) 구조 재설계 (상태 enum·TTL·핸들러 골격 유지, 저장 시 태그만 변경)
- 운영 DB 데이터 마이그레이션 (V012가 운영 미반영 — D-13-5)
- 앱에서 직접 발견→위시 변경 시 그룹원 알림 (조용히 처리 — D-13-9)

## 3. 사용자 시나리오

### 페르소나: 2인 커플 그룹 (A, B)

#### 시나리오 1 — 챗봇 단일 장소 → 위시 직저장

1. A가 카카오톡 챗봇에 인스타그램 릴스 URL을 전송한다.
2. 챗봇: "릴스에서 장소 1개를 찾았어요: • 을지로 타코집 / 가고 싶은 곳이면 위시로, 일단 둘러보기면 발견으로 저장할게요." + `[위시로 저장]` `[발견으로 저장]`
3. A가 `[위시로 저장]`을 누르면 메모 요청 후, 해당 핀이 **WISH 태그로 저장**된다.
4. 챗봇: "✨ '을지로 타코집'을 위시로 저장했어요"
5. B에게 인앱 알림: "📍 A가 위시 1곳을 저장했어요"
6. 지도 마커가 노랑 별(WISH)로 표시된다.

#### 시나리오 2 — 챗봇 다중 장소 → 위시·발견 분리 저장

1. A가 릴스 URL을 보내고 챗봇이 장소 5개를 추출한다.
2. 챗봇: "릴스에서 장소 5개를 찾았어요. ✨ 가고 싶은 곳 번호를 콤마로 보내면 위시로 저장할게요. (나머지는 발견) 예: 1,3,5 / 1. ... 2. ..." + `[전부]` `[건너뛰기]`
3. A가 "1,3"을 입력하면 메모 요청 후, 1·3번은 **WISH**, 나머지 2·4·5번은 **발견(REEL)**으로 저장된다. 메모는 저장된 모든 핀에 동일 적용된다.
4. 챗봇: "✨ 위시 2곳, 📍 발견 3곳 저장했어요 / [위시 목록] / [발견 목록]"
5. B에게 인앱 알림: "📍 A가 위시 2곳, 발견 3곳을 저장했어요"

#### 시나리오 3 — 챗봇 대량 장소 (31개+)

1. 릴스에서 31개 이상 추출되면 챗봇: "릴스에서 장소 35개를 찾았어요. 전체 발견으로 저장할게요. 함께 남길 메모를 입력해주세요. (없으면 [건너뛰기])"
2. 전체가 발견(REEL)으로 저장된다. (위시 선택 단계 없음 — D-13-4)

#### 시나리오 4 — 앱에서 직접 위시로 등록

1. A가 지도에서 발견(REEL) 핀 말풍선을 열고 ⋮ → 수정 → 태그 탭에서 [위시]를 선택한다.
2. 핀이 즉시 WISH로 변경된다. (그룹원 알림 없음 — D-13-9)

#### 시나리오 5 — 오래된 발견 핀 정리

1. A가 `/pins` 화면 하단에서 "🗑️ 30일째 그대로인 발견 핀이 N개 있어요" 배너를 확인한다.
2. 정리 대상: `tag=REEL AND memo_source=AUTO AND created_at < NOW()-30일 AND deleted_at IS NULL` (want_count 조건 제거 — D-13-7)
3. [한꺼번에 정리] → 일괄 소프트 삭제. [나중에] → 7일 snooze (기존 동작 유지).

## 8. 위험 및 가정

### 위험
| 항목 | 내용 | 대응 |
|------|------|------|
| V012 수정 영향 | 이미 로컬에 적용된 V012를 수정하면 Flyway checksum 불일치 | 로컬 도커 PG는 재생성 또는 `flyway repair` 허용. 운영 미반영이라 안전 (D-13-5) |
| 광범위 삭제 회귀 | WANT 참조가 78개 파일에 분산 → 누락 시 컴파일/런타임 오류 | grep 기반 전수 삭제 + 백엔드 컴파일·프론트 tsc로 누락 탐지 (NFR-13-2) |
| 챗봇 위시 직저장 태그 정합 | REEL로 생성 후 WISH 변경 시 중간 상태 노출 | 생성 시점 태그 직접 지정 또는 단일 트랜잭션 처리 (NFR-13-4) |
| 알림 본문 데이터 부족 | "위시 N곳/발견 M곳" 분리하려면 저장 시 태그별 카운트 전달 필요 | `ReelMemoWaitingHandler.SaveResult`에 위시/발견 카운트 분리 추가 |

### 가정
- V012는 운영에 반영되지 않았고 로컬 도커 Postgres에서만 실행 중이다.
- MVP 운영 단위는 2인 커플 그룹이다.
- 챗봇 세션 상태머신·TTL·dedup·메모 broadcast 등 Phase 12 골격은 유지하고, 저장 시 태그 결정 로직만 변경한다.
- 기존 WISH 핀(있다면)은 그대로 WISH로 유지된다.
