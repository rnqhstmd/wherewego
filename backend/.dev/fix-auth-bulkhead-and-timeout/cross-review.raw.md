# Codex Review

Target: branch diff against develop

The new bulkhead does not take effect early enough to protect the DB pool, because transaction creation happens before the semaphore acquisition. That leaves the main reliability issue this patch intends to solve still reproducible under concurrent login load.

Review comment:

- [P1] Move the bulkhead outside the transactional retry target — D:\SQ\wherewego\backend\apps\wherewego-api\src\main\java\com\wherewego\domain\auth\UserLoginPersistence.java:62-66
  When this method is invoked through the Spring proxy, `@Transactional` starts the transaction before the method body runs, so the `Semaphore` is only acquired *after* a DB connection has already been requested. In the Neon cold-start / pool-exhaustion scenario this means concurrent Kakao logins can still consume the Hikari pool and throw `CannotCreateTransactionException` before the bulkhead ever applies, which defeats the protection this change is trying to add. To actually shield the pool, the semaphore needs to wrap a non-transactional entrypoint and call a separate transactional/retryable method.
